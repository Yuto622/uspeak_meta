# 負荷テスト結果（開発環境・ローカル）

目標：**100 人同時接続**（1 ワールドに 100 人、または 4 クラス × 25 人）。いずれも切断 0 で達成。

実行：`node loadtest/run.mjs --clients=25 --duration=600`（サーバーと同一マシン、ループバック。4 vCPU / 16GB、Node 22）。
25 のヘッドレスクライアントが 20Hz でランダム歩行を送信し続け、サーバーは 10Hz で差分配信。

## 10 分間連続（600 秒）

| 指標 | 値 |
|---|---|
| 接続数 | 25 / 25（全時間帯で維持） |
| 参加所要時間 | 25 接続を 2.2 秒で参加完了（80ms 間隔の順次参加） |
| 下り帯域 / クライアント | 平均 4.30 KB/s（≒ 34 kbps）。25 台合計 ≒ 108 KB/s |
| ブロードキャスト遅延 | p50 30 ms / p95 49 ms（送信時刻 → 他クライアント受信。10Hz 配信間隔を含む） |
| サーバー CPU | 平均 約 2%、最大 2.3%（1 コア基準） |
| サーバー RSS | 85 MB → 114 MB で安定（4 分以降増加なし） |
| 切断 | 0 回 / 600 秒 |
| エラー | 0 |

> 本番（Fly.io nrt）では、遅延にネットワーク RTT（教室 Wi-Fi → 東京 で通常 10〜40 ms）が加算されます。
> 実機での再計測は `npm run loadtest -- --url=wss://<app>.fly.dev --clients=25 --duration=600 --class=loadtest` で行えます。

## 見方・目安

- 帯域 4.3 KB/s は 25 人分の位置（x, z, yaw, ts）が 10Hz で届く分。教室 Wi-Fi（数十 Mbps）に対して十分小さい。
- shared-cpu-1x（Fly の最小構成）でも CPU 2% 程度なので、1 台で複数クラスを同時に収容できる見込み。
- 遅延 p95 が 300 ms を超える、または切断が出る場合は、まず Wi-Fi の AP 容量・チャネル干渉を疑う。
  補間バッファ（`client/dist/net-config.js` の `INTERP_DELAY_MS`）を 150〜200 ms に上げると、多少の遅延揺れでも滑らかさを保てる。

### 100 人規模で入れた対策

- **描画予算**：クライアントは同じ空間の近い順に最大 32 人（`MAX_RENDERED_REMOTES`）だけ描画し、70 unit より遠い人は描画しない。
  名前ラベル・吹き出しは 35 unit 以内のみ。リモートアバターは影を落とさない（`client/dist/net-config.js`）。
- **gzip 圧縮**：`three.module.js` 1.27 MB → 258 KB。100 台が同時に開いても 26 MB で済む。
- **Fly 設定**：接続数上限 500、メモリ 1 GB（`fly.toml`）。
- 1 ルーム 100 人は下り 16 KB/s/台。教室 1 AP に 100 台は Wi-Fi 側の限界が先に来るため、実運用は「4 クラス × 25 人（別ルーム）」を推奨。
  1 ワールド 100 人はイベント用途（`MAX_CLIENTS=100`）。

## 実ブラウザ 1 画面 + ボット 99 接続（同一ルーム 100 人）

`npm run test:scale`（Chromium・ソフトウェア GL、360×240）。

| 確認項目 | 結果 |
|---|---|
| ブラウザが 99 人分の状態を追跡 | 99 / 99 |
| 描画されるアバター数 | 32（予算どおり。残り 67 人は非表示で追跡のみ） |
| ステータス | 「オンライン · 100人」、ページエラー 0 |
| 100 人在室時の切断→復帰 | 1.7 秒 |
| フレーム時間（参考） | 平均 297 ms（ソフトウェア GL のため実機の目安にはならない。iPad 実機で要計測） |

実機で重い場合は `NET_OVERRIDES='{"MAX_RENDERED_REMOTES":16,"REMOTE_CULL_DISTANCE":50}'` のように
サーバーの環境変数だけで描画予算を下げられます（コード変更・再デプロイ不要、`fly secrets set` 後の再起動のみ）。
