# フェーズ0 レビュー報告（2026-09-09）

## 結論

添付zip（USpeakRPGv11ClaudeCode.zip）には **Colyseus のマルチプレイ実装は含まれていなかった**。
ネットワーク関連コード（Colyseus / WebSocket / fetch / サーバーディレクトリ / package.json）はゼロで、
同梱の README と CLAUDE.md 自身が「サーバーDB・アカウント同期・マルチプレイはありません」
「リアルタイム通信や自由チャットはありません」と明記している。GitHub の `Yuto622/uspeak_meta` も
空（ブランチ・コミット無し）だった。

したがって「レビューして修正する」対象が存在せず、フェーズ1は **既存の1人用ゲームを壊さない追加レイヤー方式の新規実装** とした
（承認済み：生徒識別は名前入力、オフライン1人用モードは維持、永続化は Google スプレッドシート）。

## フェーズ1で採った設計

- **追加レイヤー**：`server/`（Colyseus 0.15、プレーンJS ESM）と `client/dist/net-*.js` を新設。既存ファイルへの変更は
  フック挿入（判定通知・ウォレット操作通知）と `activate()` の強制フラグ追加、`index.html` のタグ追加に限定。
- **単一ソースの正解データ**：サーバーは `client/dist/*-data.js` をそのまま import して判定する。データ複製なし。
- **サーバー権威の範囲**：クライアントは「どの問題にどの選択肢を答えたか」だけを送り、正誤・XP・コイン・捕獲・購入・学習ログは
  サーバーが確定する。クライアントの `correct` フラグやコイン申告値は一切受け付けない。
- **残存リスク（明記）**：問題文と選択肢の生成は従来通りクライアント側なので、データファイルを読める人が「常に正解を選ぶ」ことは
  防げない。これは「答えを知っている」のと等価であり、小学生の教室 iPad という脅威モデルでは許容した。
  完全に塞ぐには全問題データをサーバーに移す大規模変更が必要（今回のスコープ外）。
- **Google Sheets**：API が遅く（数百ms）レート制限（60書込/分）があるため、ルームがメモリ上の正本を持ち、
  5秒ごとにまとめて書き戻す write-behind 方式。失敗時はキューを保持して再試行。
